04Мягкая 404: мусорные URL отдают код 200 P0 · критично

Несуществующие страницы не возвращают 404 — сервер отвечает 200 OK и показывает страницу услуг. Причём неоднородно: раздел /doctors/ отрабатывает 404 правильно, а корень и даже фейковые файлы — нет.

$ curl -o /dev/null -w "%{http_code}" https://www.centr-stom.ru/nonexistent-page-xyz123/
200   ← отдаётся страница «Услуги стоматологии» (title подтверждён)

$ curl … /doctors/nonexistent-doctor-xyz/
404   ← здесь корректно

$ curl … /nonexistent.jpg
200   ← даже несуществующий статический файл → 200
Чем грозит: любой мусорный URL (опечатки, параметры, битые ссылки) попадает в индекс как «дубль». Размывается краулинг-бюджет, Яндекс/Google индексируют тысячи одинаковых страниц услуг.
Как чинить (Bitrix):
1. В обработчике 404 отдавать CHTTP::SetStatus("404 Not Found") + Bitrix\Main\Context::getCurrent()->getResponse()->setStatus(404).
2. Проверить /404.php и urlrewrite.php — сейчас фолбэк ведёт на раздел услуг.
3. Для статики — отдать 404 на уровне nginx (try_files).
4. Проверить Яндекс.Вебмастер → «Исключённые страницы / Мягкая 404».

05sitemap.xml устарел на 15+ месяцев P0 · критично

Карта сайта сгенерирована 09.08.2024 и с тех пор не пересобиралась. В ней ~104 URL — при этом блог активно публикуется (свежие статьи от июля–октября 2026) и ни одной новой статьи в sitemap нет.

<sitemapindex>
  <sitemap><loc>…/sitemap_files.xml</loc>
    <lastmod>2024-08-09</lastmod></sitemap>
  … ещё 3 индекса, все от 2024-08-09

Проверка: /blog/chto-takoe-sinus-lifting-…/  (статья 2026 г.)
→ отсутствует во всех 4 sitemap-файлах
Чем грозит: новый контент индексируется медленно (робот узнаёт о статьях только по ссылкам). Устаревшие lastmod ещё и подают сигнал «сайт не обновлялся с 2024».
Как чинить:
1. Bitrix → Настройки → Поиск → Google Sitemap: пересоздать карту, включить инфоблок блога.
2. Поставить регенерацию по расписанию (агент/cron) — при каждой публикации.
3. Добавить в sitemap разделы, созданные после 2024 г.
4. Убрать из robots.txt ручные Disallow десятков старых /news/ и /discount/ — они там «заметают следы» устаревшего контента; правильнее вернуть им 404/410.

06HTML не кэшируется: сессия стартует у всех P0 · важно

Каждый анонимный посетитель получает два PHPSESSID в одном ответе, а заголовки запрещают кэширование страницы вообще — ни браузером, ни CDN, ни композитом Битрикса.

Set-Cookie: PHPSESSID=xmTFYH4fpjp…; domain=centr-stom.ru; HttpOnly
Set-Cookie: PHPSESSID=6G6QU1g8Ufh…; domain=centr-stom.ru; HttpOnly  ← дубль!
Cache-Control: no-cache, private, must-revalidate
Expires: Thu, 01 Jan 1970 00:00:00 GMT
Чем грозит: каждый хит идёт в PHP → TTFB ~0.9 с у всех посетителей, включая роботов. При рекламном трафике (квиз/Директ) нагрузка растёт линейно. Бонус-проблема: у куки нет Secure и SameSite, а domain=centr-stom.ru раздаёт её всем поддоменам.
Как чинить:
1. Включить композитный кэш Битрикса / отключить старт сессии для анонимов (session_start только по необходимости).
2. Убрать двойной session_start — вероятно, он вызывается и в ядре, и в шаблоне/компоненте.
3. Cookie: добавить Secure; SameSite=Lax, сузить domain до хоста.
4. Цель: анонимный HTML — из кэша nginx/композита за <200 мс.

07Заголовки безопасности P1

ЗаголовокСтатус
Strict-Transport-Security✓ есть (max-age=1г, без includeSubDomains)
X-Content-Type-Options✗ нет — риск MIME-sniffing
X-Frame-Options / CSP frame-ancestors✗ нет — сайт встраиваем в iframe (кликджекинг)
Content-Security-Policy✗ нет
Referrer-Policy✗ нет — URL с utm уходят третьим сторонам
Permissions-Policy✗ нет
P3P! мёртвый стандарт (IE-эпоха), стоит убрать
X-Powered-CMS: Bitrix Site Manager! раскрывает CMS + хэш — облегчает подбор уязвимостей
Минимальный набор в nginx:
add_header X-Content-Type-Options nosniff;
add_header X-Frame-Options SAMEORIGIN;
add_header Referrer-Policy strict-origin-when-cross-origin;
add_header Permissions-Policy "geolocation=(), camera=()";
# убрать P3P и X-Powered-CMS на уровне PHP/proxy
CSP — внедрять постепенно (сначала report-only): на сайте реКапча, Метрика, Roistat, чат — все внешние домены надо перечислить.
Риск: кликджекинг формы записи (имя+телефон пациента) и сниффинг. Для медицинского сайта, собирающего ПДн, — чувствительно.

08Соцпревью и микроразметка: есть база, нет половины P1

Что есть ✓

  • JSON-LD: WebSite + Dentist/MedicalClinic на оба филиала (адреса, часы, телефон)
  • canonical на страницах, lang="ru", alt у изображений

Чего нет ✗

  • Open Graph / Twitter Cards — ноль на всех проверенных страницах: репост статьи в VK/TG/MAX идёт без картинки и описания
  • Article для статей блога — теряются расширенные сниппеты и дата в выдаче
  • Physician/Person для врачей — их страницы не выделяются в поиске
  • Review / AggregateRating на отзывах — звёзды в сниппете (сильный CTR-фактор для медицины)
  • BreadcrumbList и FAQPage — хлебные крошки и FAQ без разметки
Почему важно именно здесь: контент-маркетинг уже работает — блог пишется, статьи репостятся в соцсетях клиники (VK, MAX). Без OG каждый репост теряет превью → меньше переходов. Без Article/Review разметки сниппеты конкурентов выглядят богаче при том же контенте.
Быстрый выигрыш: шаблонные OG-теги (og:title = H1, og:image = обложка услуги/статьи, og:url, og:type) + Article на блог — это правка шаблона, не разработка. Врачи: Physician с полями specialty/worksFor из существующего JSON-LD клиники.

Замеры: Chrome headless, реальный продакшн. FCP неплохой — долгий load тянут виджеты и картинки, а не вёрстка.

  • Изображения только JPEG (~695 KB на главной). WebP/AVIF дал бы −30–50% веса. Нет srcset для ретины.
  • Кэш картинок всего 2 часа (Cache-Control: max-age=7200) — при повторных визитах всё качается заново. Для хэшированных имён файлов ставьте год + immutable.
  • Хвост load 7–9 с: reCAPTCHA грузится на каждой странице (нужна только формам), чат iiii.chat, Marquiz, Roistat. Стоит lazy-init по первому взаимодействию.
  • Нет Brotli — сервер отвечает gzip/identity; brotli дал бы −15–20% на текстовых ресурсах.
  • Редирект-цепочка: http://centr-stom.ru → https://centr-stom.ru → https://www.centr-stom.ru — два хопа вместо одного (+~0.6 с на первом визите).

10Мобильный экран перегружен виджетами P2

На первом экране смартфона (390px) одновременно присутствуют:

  • плавающие кнопки чатов — перекрывают текст оффера («консультация стоматолога за один визит»)
  • фиксированный фиолетовый баннер квиза «Рассчитайте стоимость»
  • cookie-баннер снизу

В сумме они закрывают ~40% полезного экрана. Вёрстка самой страницы адаптивна и корректна — проблема именно в наложении виджетов.

Что сделать: показывать квиз-баннер после скролла или по таймеру; объединить чат-кнопки в одну; cookie-баннер компактнее на мобильном. Замерить в Метрике (Вебвизор) — сколько пользователей закрывают баннеры вместо клика по «Записаться».

11Мелкие находки P2

  • Title главной: «…клиника в Новосибирске» — «Новосибирск» дублируется дважды + точка в конце. Смотрится как автогенерация.
  • Description главной содержит телефон коллтрекинга 8 (383) 312-06-63, а в шапке — 8 (383) 209-27-00: подменный номер зашит в meta → в выдаче показывается «не тот» номер.
  • Нет apple-touch-icon и SVG-favicon — в закладках/экране «Домой» iOS иконка будет мыльной/дефолтной.
  • robots.txt раздут вручную: десятки индивидуальных Disallow для старых /news/ и /discount/ — признак архивного контента, которому место в 404/410, а не в robots.
  • Lazy-loading частичный: loading="lazy" только у части изображений; srcset/sizes отсутствуют.
  • Висячие блоки на внутренних: у страницы-заглушки (софт-404) title «Услуги стоматологии…» — при внешних битых ссылках пользователь видит каталог вместо понятной 404 с навигацией.
  • Чат-кнопки без aria-label и плавающие элементы могут мешать скринридерам — при наличии версии для слабовидящих это стоит довести до ума.
  • Meta keywords используется — безвредно, но игнорируется поисковиками (реликт).

13Итог

Сайт свежий и продуманный по части контента и маркетинга: редизайн 2026 года, живой блог, цены, врачи, коллтрекинг, квиз. Главные проблемы — не визуальные, а инфраструктурные: мягкая 404, мёртвый sitemap, отсутствие кэша HTML и базовых security-заголовков.

Хорошая новость: всё это — конфигурационные и шаблонные правки, не требующие переделки сайта. Пункты P0–P1 закрываются примерно за неделю работы и сразу дадут чистый индекс, ускорение ответа и более богатые сниппеты в поиске и соцсетях.

Следующий шаг: передать P0-пункты разработчику/хостеру (Bitrix + nginx), затем перепроверить: код ответа мусорного URL, lastmod sitemap, заголовки — все проверки из этого аудита воспроизводимы одной командой curl.
